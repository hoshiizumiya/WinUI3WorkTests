# WinUI Essentials: first-use resource timing

Launch `WinUI3cppWorkTest` in a fresh process. `App::OnLaunched` opens `WETestWindow` directly; the window creates `TasksPageViewModel` before `InitializeComponent`, and its XAML binds the visible `ListView` to `ViewModel.FilteredTasks`. The collection starts empty. The root `Loaded` handler then calls `ViewModel.Initialize()`, which appends 500 `TaskSampleViewModel` instances to that already-bound observable vector. WinUI schedules the ListView's ordinary measure/arrange work from those collection notifications; there is no button click, `ItemsSource` reassignment, manual invalidation, or `UpdateLayout` call. This matches OpenNet's startup order: construct the view model, initialize the XAML-bound list, activate the view model on `Loaded`, then let the list realize its template.

The test XAML follows OpenNet's main task list structure: CommandBar/search row, compact filter navigation, task list and details rows, 14 header/cell positions, matching `x:Bind` property names and column visibility bindings, full-row plus progress-column `ProgressBarEx`, and virtualizing `ItemsStackPanel`. Task values are read from `TaskSampleViewModel`; progress effects use transparent base/background and per-task green/red highlights. The test keeps a local native `TaskDataRow` panel because this project does not reference OpenNet's toolkit DataTable project. It uses the same 14 positions and 16-pixel spacing, but it is an approximation rather than OpenNet's actual `DataRow` implementation.

Run each first-use scenario in a new process so another page cannot prewarm an Essential control's resource dictionary first. `WETestWindow` is now focused on the OpenNet `ProgressBarEx` list lifecycle; `MainWindow` and other sample windows remain available for independent control tests. Do not wrap the list in an outer `ScrollView`: unbounded measurement can realize every item and defeat the virtualization comparison. Scroll the list to realize later rows.

## The earlier `ItemsSource` exception

The supplied debugger trace for the previous sample ended at the projected `ListView::ItemsSource(...)` call in `RunList`, with `E_INVALIDARG`; it did not show a `Measure`/`Arrange` path or a child-collection mutation. In the warm case, the selected Essential control had already been constructed before the failing `ItemsSource` assignment. That exception therefore came from the test harness's collection hookup and did not reproduce OpenNet's reported layout exception. Changing the source to `IObservableVector<IInspectable>` removed that failure, which the user confirmed. The current sample continues to use that collection interface, but its items are now task view-model objects bound by the XAML `DataTemplate`. The exact internal validation that rejected the earlier vector is not established by that trace, so this note does not attribute it to a particular WinUI implementation detail.

OpenNet binds an observable task collection to a `ListView` whose XAML-fixed item template contains a full-row progress layer, a status/name cell, a progress cell, and 12 other detail columns. This sample uses the same two ProgressBarEx placements, the same 14 child-to-column positions, and the same DataTable spacing. The window `Loaded` event initializes the view model, which appends all sample items to the existing bound collection. This lets WinUI choose the normal layout timing. The local panel exercises custom `MeasureOverride` and `ArrangeOverride`, but it still does not use OpenNet’s actual DataTable-linked panel.

## Interpret results

- If the automatic startup list throws `Child collection must not be modified during measure or arrange`, the test has reproduced the OpenNet layout-time failure path. Capture the first-chance native exception call stack to identify which operation changed a child collection.
- If the list loads successfully, this combination of ProgressBarEx templates and layout did not reproduce the failure. A shared helper does not imply every control must throw; compare the first-use resource timing and actual toolkit `DataRow` implementation before drawing a broader conclusion.
- If the dictionary count does not rise on first construction, inspect whether another control or imported dictionary already loaded its resources before the test. Resource dictionaries may themselves merge additional dictionaries, so a delta need not equal one.

In Visual Studio, enable breaking on thrown C++/WinRT exceptions, then run the test in a fresh process; it now loads the list automatically at startup. Record the *first* application and `Microsoft.UI.Xaml.dll` frames at the throw site, not just the later `UnhandledException` callback. Do not mark the exception handled: that would mask the crash rather than identify the child mutation.
